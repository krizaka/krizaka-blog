A while ago, I asked a friend who works in IT to run an experiment with no bias. He asked three models, Claude, Gemini and ChatGPT, to look at our GitHub organisation and give an unvarnished audit. What he told me was flattering. Too flattering for me to repeat without proof.

At Krizaka, a claim has to lead to a measurement, a run or a line of code. I don't have the outputs of his experiment, so I can't quote them. So I ran it again myself, on 24 October, with a prompt written in advance and published, and an answer published as is.

## Why I ran it again

A compliment someone passes on can't be checked. A raw output can. You can reread the prompt, reread the answer, and follow every link.

I also wanted a prompt that doesn't push towards praise. It doesn't ask what is impressive. It asks for an audit, strengths and weaknesses, and says the weaknesses matter as much as the strengths. It also asks for a source for every point, and to say when the model couldn't open something rather than guess.

The full prompt is [in the appendix](#appendix-the-prompt-and-the-raw-output).

## The protocol

One model ran: Anthropic's Claude Opus 5.5, with two tools, web search and page reading. It started with no context: an empty folder, no project settings, no tool server, no memory. All it knew about Krizaka was what it read on the web during the audit.

I also have to say what didn't run.

- **Gemini.** We have no Google API key. I tried Gemini's command-line tool with my personal account: it refused, because that client is no longer accepted for individual accounts. No Gemini audit here.
- **ChatGPT.** We have no OpenAI key. No ChatGPT audit either.

That's why the title only names Claude. My friend's experiment with three models happened, but I'm not reproducing it, and I'm not quoting a word of it.

One technical detail matters when you read the answer: the page-reading tool first has the pages summarised by a smaller model, Claude Haiku 5.5. So the main model read a lot of summaries. It says so itself at the top of its answer, and adds that it checked the points that mattered most against the source code.

## What Claude found solid

Quoted word for word. The full answer is in the appendix.

On the written governance:

> "The written governance contract is unusually detailed, and CI enforces parts of it (ArchUnit, ratchets, docs-freshness check)."

On CI:

> "The CI hygiene is good: SHA pinning, least-privilege permissions, red-main alerting, nightly builds and Scorecard."

On documentation and releases:

> "Decisions are well documented, and the authors write candid self-audits."
>
> "There are real Maven Central and npm releases, with signing and release-please."

Its overall judgement, in one sentence:

> "The design and documentation are above average for a small organisation, and the CI is good."

"Above average for a small organisation." That's it. The model didn't write that it rarely sees this, or that it beats enterprise teams. So I don't write it either.

The guardrails it mentions exist, and you can read them. The ast-grep rules such as [`no-ambient-clock`](https://github.com/krizaka/krizaka-com/blob/main/rules/no-ambient-clock.yml) (no implicit clock in domain code) and [`no-enum-string-compare`](https://github.com/krizaka/krizaka-com/blob/main/rules/no-enum-string-compare.yml) (no status compared to a string). The ArchUnit rules in [`CodeRules`](https://github.com/krizaka/krizaka-build/blob/main/krizaka-test-support/src/main/java/com/krizaka/test/architecture/CodeRules.java), including `assertNoStandardStreams` (no `System.out` in production), and their counterparts in [`GovernanceRules`](https://github.com/krizaka/orazaka-build/blob/main/orazaka-test-support/src/main/java/com/krizaka/orazaka/test/architecture/GovernanceRules.java).

## What Claude found weak

This is the longest part of its answer, and the most useful.

On review:

> "The bus factor is one human. Review is effectively AI approving AI-authored code."

On the code itself:

> "The implementation is ordinary-to-uneven and further behind than the documents suggest."

On one specific file of Orazaka's job service:

> "`JobListener.java` is the weakest file I read. It is 920 lines (874 lines of code) with 16 constructor parameters."

And a real defect, in that same file: a five-second timeout for any prompt that starts with `TIMEOUT`, with no guard.

> "Any user can shorten their own job's timeout this way."

It also points out that our written rules and our code don't always agree (hand-written SQL despite the rule, a `-SNAPSHOT` version despite the ban), that two of our own audits contradict each other ([one](https://github.com/krizaka/orazaka/blob/main/docs/PRODUCTION_READINESS_AUDIT.md) says don't launch, [the other](https://github.com/krizaka/orazaka/blob/main/docs/ARCHITECTURE_ASSESSMENT.md) counts no blocker), that workspace builds follow the `main` branch of sibling repositories and so can't be reproduced, and that `@krizaka/ui` changes version too fast for a major number to still mean much.

Its conclusion:

> "The biggest structural risk is not technical: one person and a set of agents produce more code, ADRs and issues than anyone can independently review."

Everything I checked was right. The [`TIMEOUT`](https://github.com/krizaka/orazaka-job-service/blob/main/src/main/java/com/krizaka/orazaka/jobservice/infrastructure/adapter/amqp/JobListener.java#L696-L702) prefix defect is real. There was already an issue to split that file ([orazaka-job-service#50](https://github.com/krizaka/orazaka-job-service/issues/50)), but it only covered the simulation hook, which is properly behind a setting. I added what the model found: a line our own issue had missed. I fixed it the same evening: a prompt no longer chooses its own timeout; only the test simulation can, behind its setting ([orazaka-job-service#72](https://github.com/krizaka/orazaka-job-service/pull/72)).

I didn't check the rest. The claim about jobs that keep running after their timeout, for instance, the model itself says it didn't follow all the way. It stays a lead.

## The limits of the exercise

I want to be clear about what this audit doesn't prove.

- **A model can flatter.** The prompt tries to prevent it, but there's no guarantee. A sentence like "above average" is worth what an opinion is worth.
- **It only reads what's public.** It saw neither our branch protection settings (the page needs a sign-in), nor what runs in production, nor anything not pushed.
- **It read a lot of summaries.** Pages go through a smaller model before they reach it. What it says about a file it didn't open itself is less certain.
- **It's a single run.** Run again tomorrow, the same prompt will give a different answer. I haven't measured that variation.
- **Claude is auditing code largely written with Claude.** A large part of Krizaka's code is written by Claude agent sessions that I direct. The judge isn't a stranger to the case. That's one more reason to run the experiment again with other models, and I will once we have the keys to do it properly.

It's not a proof. It's an outside reading, published with its sources, that anyone can run again.

## What I take from it

What my friend had told me was about being agnostic, and about a small army of coding agents with one person directing and reviewing. I had never seen that as a skill of its own. It just felt like the normal way to work.

Thinking about it again, I believe it has to do with cognitive ergonomics. Stepping back, looking at a system from above, finding where it rubs, drawing clear boundaries, and organising the work between a person and machines so that a mistake shows up right away. It probably comes from my studies, mathematics and computing applied to cognitive science, and from the speed at which agents produce code. Someone from IT reminded me of a sentence I wrote a while ago:

> "To build effectively with AI, you must structure your automations to detect errors as early and as fast as possible."

That's fail fast. An agent writes quickly. Rules, types and architecture tests say no within seconds, before the mistake spreads.

The audit also shows where that principle stops for us. Our guardrails catch what we wrote a rule for. They don't see what we haven't named yet. The `TIMEOUT` line broke no rule. And a rule only looks where it's told to look: in Yomizaka, a date computed in UTC instead of the Québec day slipped past `no-ambient-clock`, because the rule didn't read that folder. It took a new rule, [`no-utc-day-slice`](https://github.com/krizaka/yomizaka/blob/main/rules/no-utc-day-slice.yml), written after the bug ([yomizaka#311](https://github.com/krizaka/yomizaka/pull/311)). Our own inventory, [`docs/quality-controls.md`](https://github.com/krizaka/.github/blob/main/docs/quality-controls.md) ([.github#232](https://github.com/krizaka/.github/pull/232)), opens with that very sentence: "The rules do not look where the bug was."

On review, the model is right, and I don't have a full answer yet. I review and approve, but I'm alone, and some approvals go through an agent I've delegated decisions to. The automated checks are real. A second pair of human eyes isn't. That's the point of this audit I keep coming back to.

## Appendix: the prompt and the raw output

The audit ran on 24 October 2026, from 23:53 to 23:58 UTC, with Claude Code 2.1.308 in headless mode, the model `claude-opus-5-5`, and only the WebSearch and WebFetch tools. The published files are untouched:

- [the prompt](https://blog.krizaka.com/audits/2026-10-24-ai-audit/prompt.txt);
- [Claude's full answer](https://blog.krizaka.com/audits/2026-10-24-ai-audit/claude-opus-5-5-answer.md), uncut;
- [the run details](https://blog.krizaka.com/audits/2026-10-24-ai-audit/run.json): the command, the models, the tokens, the cost, and what couldn't run.

The prompt, as sent:

```text
You are reviewing a software organisation you have never seen before. Use your web tools to read it yourself; do not rely on prior knowledge of it.

Target: the public GitHub organisation https://github.com/krizaka

Please:
1. Look at the organisation page and the list of its public repositories. Open the repositories you judge most important (for example their README, a few source files, the CI workflows, any architecture or decision documents, and recent pull requests or commits).
2. Give an unvarnished technical audit of what you actually read: the architecture, code quality, testing, documentation, and the engineering setup (CI, automated checks, release process, governance).
3. List the strengths and the weaknesses. Weaknesses are as important as strengths: name risks, gaps, inconsistencies, things that look unfinished, and anything a careful reviewer would worry about.
4. For every point, say which repository, file or page it is based on (a URL), so a reader can check it. If you could not open something, say so instead of guessing.
5. End with a short overall assessment and the three changes you would make first.

Be specific and neutral. Do not flatter and do not soften criticism. If something is ordinary, say it is ordinary.
```

The tokens, as the tool counted them:

- **Claude Opus 5.5**: 30 input tokens, 47,862 written to the cache and 416,449 read from it, 14,027 output, so $0.61.
- **Claude Haiku 5.5**, for the page summaries: 481,596 input tokens and 79,082 output, so $0.09.
