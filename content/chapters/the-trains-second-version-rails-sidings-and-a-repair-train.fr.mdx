Au [chapitre 19](/fr/story/tchou-tchou-how-our-pull-requests-catch-the-train/), j'ai raconté nos premiers trains : un petit script qui fait atterrir les pull requests une par une, sans jeton de modèle. Il a tenu une semaine. Du 1er au 3 novembre, il a cassé de quatre façons que je n'avais pas prévues, et je l'ai reconstruit. Ce chapitre montre la nouvelle version avec des dessins de trains, parce que c'est comme ça que je la vois dans ma tête.

Une précision avant de commencer. Nos produits portent ici des noms de code : Produit A, Produit B, Produit C, et la plateforme. Ce qui compte, c'est la mécanique, pas les noms.

## Quatre moments de la fin de semaine

**Des PR vertes qui n'arrivaient jamais.** Le 1er novembre, des PR attendaient depuis des heures, tous les checks verts, et rien ne les portait. Les trains de l'époque n'avaient pas d'ordre : plusieurs se disputaient le même dépôt, une PR en avait deux, et certains tournaient depuis deux jours sur une PR bloquée en cachant celles qui étaient prêtes derrière.

**Un main rouge qui bloque tout le monde.** Quand la branche principale d'un dépôt devient rouge, toutes les PR ouvertes le deviennent aussi, même celles qui n'y sont pour rien. Le 2 novembre au soir, sur la plateforme, trois PR étaient rouges pour la même raison : une mise à jour automatique de la semaine avait fait dépasser un budget de taille sur main. Aucune des trois ne pouvait passer, et les relancer ne servait à rien.

**La réparation refusée par notre propre outil.** La session qui a corrigé main a voulu ouvrir sa PR. L'outil d'ouverture l'a refusée : elle touchait les mêmes fichiers que les PR qu'elle venait débloquer. C'est une bonne règle d'habitude, elle évite deux PR qui se marchent dessus. Mais ici, elle bloquait la seule PR qui pouvait tout remettre en route.

**Une session morte sans bruit.** Le 2 novembre vers 9 h 45, une de nos sessions s'est arrêtée net sur la limite d'usage hebdomadaire du modèle. Rien n'a sonné. Sa fiche est restée ouverte pendant des heures, la passation suivante disait qu'aucune session ne tournait, et son coût n'a jamais été enregistré.

## Les rails

La nouvelle version tient en une image. Chaque produit a son rail. Sur chaque rail, une seule file, ordonnée : la PR la plus ancienne devant. Trois PR au plus sont actives par dépôt, les autres attendent hors de la fenêtre. La gare, c'est main.

  <Beat>Trois PR au plus sont actives par dépôt. Les autres attendent, et entrent quand une PR arrive.</Beat>
  <Beat>Toutes les trois minutes, le chef de train regarde la PR de tête : à jour avec main, checks verts. Il l'approuve et la met dans la file de fusion.</Beat>
  <Beat>La file de fusion refait passer les checks sur le résultat fusionné. La PR arrive sur main en un seul commit, et sa branche est supprimée.</Beat>

Le chef de train ne juge pas le code. La relecture se fait avant, par la session qui a écrit la PR. Lui fait le travail de quai : attendre, mettre à jour, approuver, mettre en file. Et surtout, il ne reste jamais bloqué derrière une PR qui ne partira pas.

## Le pire

C'est là que la nouvelle version change tout. Avant, une PR rouge en tête arrêtait le train, et tout ce qui était derrière attendait. Maintenant, la PR rouge est sortie du rail, mise sur une voie de garage avec sa raison écrite, et la suivante part.

Le main rouge a sa propre règle. Si main est rouge, une PR verte ne prouve plus rien : ses checks ont tourné sur une base cassée. Le rail est gelé. Seul un train a le droit de passer, le train de réparation, une PR dont le titre commence par `fix(main)`. Il passe devant tout le monde, hors plafond, et depuis le 3 novembre l'outil d'ouverture ne le refuse plus quand il touche les fichiers des PR qu'il débloque : il le note, et ces PR se remettront à jour derrière lui.

Le dernier cas vient d'une vraie perte. Avant cette règle, deux PR empilées se sont fermées toutes seules : leur base avait fusionné, sa branche avait été supprimée, et GitHub ferme une PR dont la base n'existe plus. Le travail était là, la PR non.

## Qui fait quoi, et ce qui coûte

Je travaille avec des agents. Un pilote lance les sessions, une par produit, une pour la plateforme, une pour la sécurité. Chaque session écrit le code, lance les checks, ouvre sa PR, écrit sa passation et s'arrête. Ces deux-là sont des modèles : ils coûtent des jetons.

Tout le reste est un script. La file et le chef de train roulent dès qu'une PR attend. Le contrôleur, qui chasse les trains en double et les têtes coincées depuis une heure, et le veilleur, qui lit et écrit ses alertes, passent toutes les quinze minutes. Aucun ne coûte de jeton de modèle. Deux applications GitHub ouvrent, approuvent et mettent en file. Aucun compte humain ne travaille en arrière-plan.

La session morte du 2 novembre a laissé sa garde. Une session note maintenant, en démarrant, son processus et sa transcription. Le veilleur la déclare morte quand le processus a disparu ou quand la transcription finit sur une erreur, comme une limite d'usage, et figée quand elle se tait depuis plus d'une heure. Elle est fermée proprement, et son coût est lu dans ce qu'elle a vraiment fait.

## Ce que disent les journaux

Chaque file écrit une ligne par événement. Entre le 1er novembre à 17 h 43, quand les files par produit ont démarré, et le 3 novembre à minuit, soit un peu plus de 30 heures, les trains ont fait arriver 267 PR sur main. Ils en ont mis 196 de côté, chaque fois avec une raison :

| Raison | Fois |
| :--- | ---: |
| un check rouge | 141 |
| sortie de la file de fusion | 15 |
| un check requis qui n'a jamais tourné | 13 |
| un conflit | 12 |
| main rouge, rail gelé | 10 |
| déjà portée par un autre train | 4 |
| un train de plus de 24 heures | 1 |

Une PR mise de côté n'est pas une PR perdue. Elle revient quand on pousse un nouveau commit, ou quand main redevient vert. Ce que montre ce tableau, c'est 196 fois où, avant, tout le rail se serait arrêté.

Le veilleur, lui, a écrit 359 lignes d'alerte depuis le soir du 1er novembre. Les plus fréquentes : 122 fois une PR rouge ou en conflit sans responsable, 56 fois un main rouge depuis plus de trente minutes, 38 fois un rail gelé avec des PR vertes qui attendaient. Aucune n'a coûté un jeton. Elles disent seulement à une session où regarder.

Pendant ces mêmes 30 heures, 49 sessions de modèle ont été enregistrées. Leur coût en jetons était, jusqu'au 3 novembre, une estimation tapée par la session elle-même ; depuis, il est mesuré. Je ne donne donc pas de « jetons économisés » : je n'ai pas de mesure honnête de ce qu'aurait coûté une session qui attend la CI. Ce que je sais, c'est qu'aucune n'attend plus.

## Ce qui reste

Le rail gelé dit que main est rouge, il ne le répare pas : il faut encore une session pour écrire le `fix(main)`. Le plafond de trois PR par dépôt bloque parfois une bonne PR derrière deux PR rouges, et la réponse reste humaine, faire passer ou fermer. Et le veilleur prévient, il ne décide pas. C'est voulu : un script qui ne coûte rien peut surveiller tout le temps, mais réparer reste le travail de quelqu'un.
