A few days ago, a prospect research Studio turned green on Orazaka. Status: succeeded. We opened the result, and the ranking was empty. So was the summary.

Nothing had crashed. The model had answered, every step had returned something, and the engine had done exactly what it was told: move to the next step, then call the run done. The trouble is that « something » could be nothing.

The same day, an authenticity check on Yomizaka returned its signals flattened into one line of text. And a test account saw its free audit spent by a run that had failed. Three symptoms, one cause: the engine knew how to say « finished », not how to say « right ».

## Reread before rewriting

Before touching the code, I had the engine reviewed, then checked every remark against the real code. It is a step I no longer skip. A good half of the proposals already existed: conditions on a step, loops with a parallelism cap, human approval steps, the refund when the fault is ours. One was simply wrong: we were told a hosted model was hard-coded, which had not been true for a long time. We added a test anyway, so it never becomes true.

What was left fit in one sentence, and it became the rule of v2: **a run never delivers an empty result as a success.**

## The output contract

A step can now declare the shape of what it must return. Not a full JSON Schema, a small closed subset: types, required fields, a minimum length. A keyword the engine does not check is refused at publication, because a rule silently ignored is a promise nobody keeps.

```json
{
  "id": "write",
  "kind": "CAPABILITY",
  "featureKey": "orazaka.core.chat.completion",
  "onError": "RETRY",
  "maxAttempts": 2,
  "outputContract": {
    "type": "object",
    "required": ["content"],
    "properties": { "content": { "type": "string", "minLength": 1 } }
  }
}
```

When the step comes back, its output is checked before it is marked succeeded. Outside the contract, the step fails with a message that names the field and the rule, never the value (in a regulated pack, the value is what a person wrote). Its retry policy applies. If it fails again, the run fails and the reserved credits go back. We do not bill an empty result.

The contract already existed for the run as a whole. Rather than write a second mechanism, the step reuses the very same one. It is a habit I try to keep everywhere: when something exists, use it, do not copy it.

## The other changes

**Collected loops.** A step can run over a list, say one description per photo. The next step received those results badly: it needed each item's fields, in the order of the items, not in the order they came back. That was the real cause of the empty ranking at the start.

**The exact cache.** The same file, the same Studio version, the same configuration: the result already computed comes back at once, with no credits held and no model called, and it says which run it comes from. No « similar document »: an exact fingerprint. The administrator turns it on Studio by Studio, because only a deterministic Studio may answer the same thing twice. Today, that is Yomizaka's authenticity check.

**A Studio that calls another.** A step can call a published Studio. The child run has its own id, its credits stay inside the parent's reservation, and its failure becomes the step's, which the parent's policy handles like any other. One level only: a Studio that calls others cannot be called, or a run could go round in circles.

**Resuming from a step.** A run that failed at step four, or whose last step you want redone, starts again from there. The earlier steps keep their outputs, the new run points to the original, and only the steps that run again are billed.

## What comes next

The next piece is speed and configuration. Today the engine rereads a Studio's definition every time a step finishes, though a published version never changes. Every engine setting (caps, cache, concurrency) already lives in the database, but there is no screen yet for the administrator to change it without me. And model routing must be able to say « local only, never a hosted provider », with a fallback model inside the same rule.

I cut those into precise issues and handed them to coding agents on GitHub, which comment their progress on each issue. I review everything that comes back before merging. A later post will show what it really gives, numbers before and after.

The engine is the part nobody sees. But it is the part that decides whether a green screen means anything.
