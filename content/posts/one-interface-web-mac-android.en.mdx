Orazaka has a web client, an app for phones and a Mac app. If we had to draw every screen three times, we would never finish, and after a month the three would no longer look alike.

This post tells how the code is organised so that does not happen: what is shared, what stays local, and what I saw change when these apps moved closer to [Krizaka UI](https://ui.krizaka.com). It complements [the post about the kit](/posts/krizaka-ui-one-kit-three-platforms/), which gave figures. Here I look at the apps' code. I end on the direction we are taking, and I want it read as a direction, not as a promise.

## What is shared, layer by layer

I read it in the three apps' `package.json` files.

**Tokens.** Colours and themes come from `@krizaka/tokens`. The package has a CSS output for the web and a `native` entry for React Native. A colour is changed in one place.

**Components.** `@krizaka/ui` for the web, and the same window for the Mac app. `@krizaka/ui/native` for the phone. The names are the same (`Button`, `Badge`, `Card`, `Header`, `TextField`), and so are the variants. The mobile app makes about forty imports from `@krizaka/ui/native`, and its local interface folder now holds only four small files, 177 lines in all: the frame of the sign-in screens, a settings row, a theme wrapper, a styles hook.

**Contracts.** `@krizaka/orazaka-shared` holds the TypeScript types and Zod schemas of what Orazaka's API exchanges: jobs, their steps, and since 20 October the automations, their triggers and their runs. The web client and the mobile app both depend on it. If the API changes, both change at the same moment, and the compiler says so.

**Words and languages.** `@krizaka/intl` and `@krizaka/i18n` for formats and texts, in English and French, on the web and on mobile.

**The plumbing.** `@krizaka/query` for requests, and `@krizaka/discovery`: the mobile app does not know the server's address, it reads it from a signed manifest at start.

**Orazaka's identity.** `@krizaka/orazaka-design-system` is Orazaka's orange theme, written as overrides of the kit's tokens, with a few product-specific components. The Mac app loads its theme. The design system does not replace the kit, it sits on top and re-exports its building blocks.

## What stays local

What an app cannot share is what it does. On the phone, the `core` folder keeps the logic: the flow of a conversation, the form of a run, the computing of a report, the upload of a photo. The repository's rules point the same way: no hand-written colour, no component over 250 lines, types that come from `orazaka-shared` and nowhere else.

That is the kind of sharing I like: the kit does the same thing everywhere, and the app only does what is its own.

## What I saw change

Three small examples, from the mobile app's history.

The Studios' photo fields use the kit's media picker (camera roll or camera) instead of code of our own ([#34](https://github.com/krizaka/orazaka-mobile-client/pull/34)).

The phone's tab bar takes the web rail's words and order, minus Home, Packs and Usage: Studios, Chat, Jobs, Settings ([#38](https://github.com/krizaka/orazaka-mobile-client/pull/38)). A test pins its shape, four tabs, so a change cannot slip through unseen.

And when the kit took on the "Cahier" identity (badges and buttons with sharper corners), some tests of Orazaka's component library broke: they checked a radius value. We fixed them to check the variant, not the radius ([#54](https://github.com/krizaka/orazaka-ui-kit/pull/54)). A test that pins a visual detail breaks every time the kit evolves, and that is not what we want it to watch.

## Android and iOS: one codebase

The phone app is an Expo project, in React Native. Android and iOS come from the same code. In the build configuration, one profile produces an APK file for Android, another a TestFlight build for iOS. The adaptive Android icon is made from the brand's marks, and the app handles universal links (App Links on Android).

I say nothing more: I have not checked a store release.

## The same interface, not the same layout

The same interface does not mean the same screen. On the web, an application's navigation is a rail of icons on the left. On a phone, that rail becomes a tab bar at the bottom ([the kit's changelog](https://github.com/krizaka/krizaka-ui/blob/main/packages/ui/CHANGELOG.md) says so for `RailNav`). On the Mac, it is the web form in the window, and the kit provides a title bar and a desktop density for it, as I told in [the post about the Mac app](/posts/why-orazaka-has-a-mac-app/).

What is common is the contract: the names, the states, the tokens, the words. What changes is the shape an element takes depending on the machine.

The kit enforces that discipline. Every component has to say, for the web, the phone and the desktop, whether it exists there, whether it is still to build (with an issue), or whether it makes no sense there (and what answers in its place). A component without that decision fails the tests. The matrix can be read on [the platforms page](https://ui.krizaka.com/platforms) of Krizaka UI's site.

## What it costs

Gaps remain between the web and the phone. One I know: a button's text goes through `label` on the phone, through its children on the web. Small, but it is a difference someone will pay for one day.

Every kit version has to be bumped in every app. In the mobile app's history there are small version-bump commits, from 3.21 to 3.30 between 17 and 20 October. That is the price of sharing: the app gets every kit fix, but only when it is bumped.

And on the Mac, as I wrote, the app still uses only a small part of the kit.

## Where we are heading

The direction is for the same interface contract to hold everywhere: web, Mac, Android, iOS. One component, one name, variants, states and tokens, and the shape each machine gives it.

I promise no date and I promise no complete coverage. What I would like to do next: reduce the gaps in the matrix, bring property names closer between the web and the phone, and have the Mac app adopt the kit's desktop form.

If it did not work, I would see it in this: a screen that needs behaviour specific to one machine, with no way for the kit to express it. Then the thing will have to be added to the kit, not copied into the app.
