This week a code repository is retiring: `orazaka-web-admin`. It was Orazaka's admin console, the one place where you suspend an account, change a price or publish a Studio. It had always lived in its own application, with its own repository. It is now moving into Orazaka's web application, and Orochia's console made the same move.

This post tells why it was separate, what it can do today, why we are putting it somewhere else, and what that costs us. I end on a question I have no answer to.

## A separate console

An admin console is the most powerful door of a product. Whoever gets in can do anything. So I wanted it to look nothing like the other doors.

Orazaka's has four rules, which I re-read in the code before writing this.

**It only answers a list of addresses.** Before anything else, the application's proxy compares the caller's address with a list read from the environment. Any other address gets a 403, sign-in page included ([`edge.ts`](https://github.com/krizaka/orazaka-web-client/blob/main/src/console/core/edge.ts)). A sign-in page that nobody else can reach does not have to be defended against everybody. Only `robots.txt` gets through, and it says "Disallow: /"; every answer also carries `noindex`.

**The role is checked on the server.** There is no social login. An account without the administrator role does not get a console session, and every administrative endpoint checks that role again on its side, whichever client calls it ([the administration page, generated from the code](https://github.com/krizaka/orazaka/blob/main/docs/_generated/ADMIN.md)).

**The browser never sees a service.** The console is a server-side proxy: the application adds the session token to the call, not the page. And the internal routes (credit holds and settlements, for example) are simply not in the edge's route table. The console cannot reach them, by construction.

**It has its own session secrets.** A cookie, a signing key and a sign-in switch of its own, distinct from the public site's. If sign-in is closed, the console's API routes answer 404.

Orochia's console went further. It has **one account**, defined by the environment: nobody signs up, there is no other user, so there is no user management to attack. It has **its own small database**, holding only that account, its sessions and the log of the operator's decisions. It never reads Orochia's database: it calls the platform's admin API as a service, with a token, on admin routes only ([Orochia's `AGENTS.md`](https://github.com/krizaka/orochia/blob/main/AGENTS.md)).

What I was after with all this fits in one sentence: the console should only be able to do what the admin API accepts, and a stolen password should not hand over the database. That is not a proof of security. It is a reduction of what an incident can touch.

## What the console does today

For Orazaka, this is what I found in the code, screen by screen.

**Accounts.** Search an account, suspend it or restore it, give it or take away the administrator role. Export its data (the access right of Law 25) and erase it. To erase, you have to type the account's e-mail address again: the button stays disabled until it matches.

**Billing.** Consumption by capability and by model, refusals included. Plans, which you create or retire, and business packs, which you publish or withdraw. The price book: you preview a version before publishing it. Credit wallets, where you adjust a balance (the console knows how many adjustments were made today), and subscriptions, which you can cancel at once or at the end of the period. And the billing settings.

**Models.** The registry of models and their providers, and the capabilities you can switch on or off without a redeploy.

**Studios.** The blueprint editor: versions, drafts, publishing a version, usage analytics.

**Operations.** The platform's health, the state of its dependencies, queue depth, recent errors, the deployed version.

**Audit log.** One view that gathers the trails of accounts, billing, Studios and the engine. **Tasks**: what needs a human, meaning refused or failed actions with no success since, and failed jobs.

Two limits. The console's screens are still in French only. And the audit log is not yet what I want: one thread, with a request id from end to end. That is [decision 085](https://github.com/krizaka/orazaka/blob/main/docs/adr/ADR-085-operator-audit-trail.md), and it is still marked "proposed".

## Why it is moving into the app

On 21 October, Orazaka's console stopped being an application. It is served by the web application, on its own address, depending on the host name asked for. The old application stays on for 48 hours as a way back, until 23 October, then goes away.

The reasons are ordinary, and I prefer to say so.

One service less to run, deploy and watch, for a console that a few people open.

One version bump less. Every version of the interface kit had to be bumped in the console like in the other applications: the console repository's history counts six such commits between 17 and 20 October.

And screens that already spoke the same language. The console and the web client use the same typed contracts, those of the shared package `@krizaka/orazaka-shared`. Keeping them in two repositories meant coordinating two versions of the same vocabulary.

What had to stay true is the isolation. It is now written in code, no longer in infrastructure. A pure function decides, from the host name, whether a request goes to the console or to the public site. On any other host, every console address answers 404. The address list runs before any console route. The cookie, the key and the sign-in switch stay separate. And a test ([`host-routing.test.ts`](https://github.com/krizaka/orazaka-web-client/blob/main/src/__tests__/host-routing.test.ts)) checks these rules, including that an empty list in production refuses everyone.

What it costs, honestly. The console is in the same program as the public site: if one goes down, so does the other. And the separation now rests on one rule that we wrote and tested. A mistake in that rule and the console would be seen from the wrong side. Before, you had to be wrong twice.

## The question I have not settled

I have two questions, and I have not decided.

The first: should a console be a separate application, or a door inside the application? I just chose the door, for simplicity. I am not sure it is the right choice once the product grows and more people use the console than today.

The second: is a list of addresses a good lock? It is simple, and it stops everyone before the sign-in page. But an address is not a person: it changes when someone changes connection, and it is shared in an office. A lock based on the person's identity, placed in front of the application, would hold better on that point. It also adds one more party to trust.

If you run an admin console, how do you protect it, and what would you do differently? Write to me through [the contact page](https://www.krizaka.com/en/contact). I will read everything, and I will tell what we end up choosing.
