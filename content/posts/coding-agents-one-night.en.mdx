Last night I tried something I had been putting off. Instead of moving issues forward one by one, we handed about thirty of them to coding agents on GitHub. Components for Krizaka UI, animations, fixes in Orazaka's engine, screens for Akinaza, a legal review of our terms. Each agent starts from an issue, opens a branch and comes back with a pull request.

A few hours later I should have found a stack of PRs ready to review. Mostly I found things that had broken. Not because of the agents, for the most part. Because of us.

## Empty PRs

Five PRs, on Akinaza and Yomizaka, had a title, a fine description of the work, and zero files changed. Reading one session's log, I found the last line: the work was done and committed, but the push had been refused.

Our repositories run a full check before every push. That check included a test that read the list of our icons from our CDN. The agent works in a sandbox with no Internet access beyond a few addresses. The test failed, the push was refused, and the work stayed in the sandbox. Lost.

The fix was simple. The test now compares our icons with a committed file of hashes, with no network. The comparison with the CDN still happens, in CI, which has the network. We weakened nothing. We put each check where it can run.

## CI that never ran

Other PRs had content and tests, and stayed blocked. They were not red. They were nothing: the required check had never started. On GitHub, a push made by an agent waits for a human to approve the workflow run. Nobody had, and nobody could see it.

Until the right setting is in place, our own GitHub app pushes an empty commit to the branch, and CI starts. It is not elegant, but it is written down, and everyone knows why.

## Java that did not compile

The PR that taught me the most came from the engine. An agent had optimised the hot path of Orazaka's saga: fewer queries per step, a cache of Studio definitions. On paper it was well thought out. Except the code did not compile, and the formatter had never been run.

The agent had not worked badly. It had simply never been able to build the project. An Orazaka component does not build alone: its parent POM and its upstream modules come from the full workspace, and the agent only had the component's repository. It said so itself in its PR, in one line. It pushed anyway.

We wrote an action that sets up the workspace before the agent starts: it clones the repositories, installs the upstream modules and links the packs beside its checkout. Every Java repository calls it. An agent that cannot build cannot check, and an agent that cannot check should not push.

## A prompt that invented things

For the legal review, I asked Orazaka, our own engine, to write the agent's prompt. The plan was good. But it named two repositories that do not exist, government links that do not exist, and a 14-day cancellation rule it attributed to Québec's consumer protection law. It does not come from there.

We corrected it before publishing the issue, and left the raw output as a comment, so anyone can compare. That is exactly the kind of mistake a legal document cannot afford, which is why the agent got a clear instruction: what it cannot verify, it marks « to validate by counsel ».

## The rules we wrote

All of this now fits in one section of our engineering charter, the one every repository in the organisation inherits. Build before you push, and if you cannot, say so and stop. Comment your progress on the issue, because that is where I follow the work. Tests that need no network. Invent nothing. Never weaken a guard to get green, even when that guard lives in another repository. And let the administrator set every parameter, instead of writing it in the code.

None of these rules is new for a human. What changes with an agent is that it arrives with no context. What we do not write down, it does not know.

## The DevOps

One more thing came out of that night. While trying to fix a few repository names, I realised a repository's name is written in dozens of places: in the CI pipelines, in the workspace manifest, in the deployments, in the site's data. Renaming a repository today is a treasure hunt.

So we are building a kind of build pack for CI. Every repository will have one line:

```yaml
jobs:
  ci:
    uses: krizaka/.github/.github/workflows/krizaka-ci.yml@v2
    secrets: inherit
```

The rest is decided by our actions: they look at what the repository holds (a Java project of the workspace, Node, Python, infrastructure) and run the right pipeline. A single registry of repositories replaces the hand-written names, and a script lists everything that names a repository before it is renamed.

An agent is building that right now, in the role of DevOps, within a narrow scope and deploying nothing. I will review its PR like the others. I will tell you in a later post whether it held.
